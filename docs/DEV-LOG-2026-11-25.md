## 二、为什么不用「点插」而是「巡检 + 状态跃迁」

任务进入终态的地方有六七处：rclone job 回调、目录 worker、转封装、跨账号转移、解压、卡住看门狗、低速重连用尽。
在每一处插一句「发通知」看起来最直接，但：

1. 新增一条终态路径（以后再加重试/中转）忘了插，就静默不通知，且没有任何地方能发现；
2. 没法统一去重，用户点「停止」和「故障停止」也分不开；
3. 单测只能覆盖到具体那几处分支。

改成常驻线程每 5 秒读一次 `jobs.json`，比较「上一轮见过的终态」与「这一轮的终态」：

```
notify_loop()  → 每 NOTIFY_SCAN_SEC(5s) 调 notify_scan()
                  → 首次运行只登记（seeded=True），一条都不发
                  → 之后新的去重键才发，一批之间 sleep NOTIFY_SEND_GAP(1s) 防限流
                  → 发送失败也写进去重表，避免同一任务每 5 秒重试刷屏
```

代价是最坏晚 5 秒才知道任务结束 —— 对一个下载器无所谓，换来的是「任何新增终态路径都自动被覆盖」。

## 三、事件判定口径（关键）

| 任务终态 | 条件 | 是否推送 |
| --- | --- | --- |
| `done` | — | ✅ 标题「云梭｜下载完成：<名>」 |
| `error` | `error` 非空 | ✅ 标题「云梭｜任务失败：<名>」 |
| `stopped` | `error` 非空 | ✅ 任务失败（额度用尽 / 卡住看门狗 / 低速重连用尽 / 重启中断都落在这里） |
| `stopped` | `error` 为空 | ❌ 用户自己点的停止，推了就是噪音 |
| `running` / `queued` / `paused` / `stopping` | — | ❌ 非终态 |

去重键：`"<任务id>|<state>|<bytes>|<error 前 60 字>"`

- 同一终态重复扫描 → 同键 → 不重复发；
- 点「继续」后 `bytes` 变了、或错误文案变了 → 换键 → 重新推（这是刻意的，第二次失败值得知道）；
- 状态文件 `DATA_DIR/notify-state.json`（容器内 `/app/notify-state.json`，宿主 `/vol1/docker-apps/console/notify-state.json`），最多保留 400 条，滚旧丢新。

## 九、v4.11 补修（同日晚，两处通知噪音）

### 9.1 部署 v4.11 之前的 v4.10 就暴露了两个问题

**问题一：重启容器 → 一串「任务失败」。**
11:12 重启 v4.10 后，日志立刻出现 `已发送 2 条任务通知`。查去重表，发的是两条
`stopped|…|控制台重启过，下载已中断（点「继续」会跳过已完成文件接着传）`。
原因：v4.10 的口径是「带 error 的 stopped = 故障停止」，而重启中断恰好带 error。升级一次就发一串失败，显然不对。

**问题二：老任务正文写「文件：0/0 个」。**
rclone 老任务与单文件任务没有 `filesDone` / `filesTotal`，`notify_content` 里 `("%d/%d") if total` 的分支落到 `else`，
渲染成 `0/0`，读起来像下失败了。

### 9.2 改法

- `notify_event`：`stopped` 且 error 以 `("控制台重启过", "守护进程重启过")` 开头 → 返回 `None`，不推。
  三种重启文案（下载中断 / 解压中断 / 转移中断、守护进程重启）都被这个前缀覆盖。
  真正的故障停止（额度用尽 / 卡住看门狗 / 低速重连用尽）文案不带这些前缀，照旧推。
  界面上状态与错误原文不变，只是不发微信。
- `notify_content`：「文件」行改为按数据可用性渲染 —— 有总数→`5/7 个（失败 2）`；只有完成数→`3 个（失败 1）`；
  单文件且成功→`1 个`；都没有→**整行不显示**。

## 十一、v4.13 失败任务自动重试

需求：任务失败后等 X 分钟自动重新开始。

### 11.1 口径（为什么不是「error 就重跑」）

| 状态 | 处理 |
| --- | --- |
| `error`，普通失败（网络瞬断 / 5xx / 连接僵死 / 云端临时报错） | 等满 `autoRetryMin` 分钟点一次「继续」 |
| `error`，文案含 重新登录 / 登录失效 / captcha / 人机验证 / 额度 / 流量已达 / 存储空间保护 / 空间不足 / 磁盘 | 跳过（重试救不了，还可能加重风控） |
| `stopped`（手动停止、重启中断） | 不碰 |
| `done` | 顺手清零重试计数 |

### 11.2 实现要点

- 线程 `auto_retry_loop()`，30 秒一拍；等待粒度由 `autoRetryMin` 决定，与扫描间隔无关
- 首次看到失败只打 `_arErrAt` 时间戳（重启后也从头等，不会立刻重跑）；满 N 分钟才动手
- 真正「继续」用的是**回环 HTTP**：`POST /api {"action":"resume","id":…,"_auto":true}`。
  不用另写启动逻辑，是因为「继续」里绑着旧线程退出检查、目标卷磁盘保护、云端源目录预检（要联网列目录）、
  并发槽位与排队判断 —— 复制一份迟早跑偏。因此必须先放锁再发请求（api 处理时自己拿 `LOCK`，持锁调用死锁）
- 计数：每次成功发起 `_arTries+1` 并清 `_arErrAt`；「旧工作线程还没退出」不算一次尝试；点不动（磁盘保护 / 源目录空）算一次
- 人工点「继续」通过 `_auto` 标记区分，会把 `_arTries` 清零；任务成功一次也清零
- 设置项 `autoRetryOn` / `autoRetryMin`(1~1440) / `autoRetryMax`(0~10)，进白名单与 `_norm_settings`；
  设置页独立一块，放在「微信通知」上方，默认可见、默认**关**

## 十二、v4.14 账号失效 / 重新登录 / 人机验证也纳入自动重试

v4.13 把这三类判成「跳过」。实际情况是 PikPak 的 captcha 风控多数换个 `device_id` 就能过，
凭证被 rclone 轮换后镜像不同步也会报「请重新登录」—— 不是救不回来，是「只重试、不修账号」救不回来。

改法：

- 新增 `AUTO_RETRY_CRED_RE`（重新登录 / 登录失效 / captcha / 人机验证 / unauthorized / 401 / refresh_token / 凭证）
- 命中就先跑 `pikpak_verify(账号)`（`allow_repair=True`：自动换 `device_id` 再试一次、同步被轮换的凭证），
  修好才点「继续」，日志打「任务 N 的账号「X」已修复（…），接着重试」

## 十五、v4.17：进度条一会长一会短 —— 两代 worker 并存（次日 01:00–01:40）

### 症状
用户贴了两张同一任务（`Leedm黎梦`）的卡片截图：一次 27.0% / 2.95 GB / 2-9，一次 67.3% / 7.35 GB / 5-9。

### 实测证据（每 15 秒采样一次，90 秒）
```
t00 31.0% 3.66GB 2/9  ->  t01 70.9% 8.31GB 5/9  ->  t02 71.1%
t03 31.5% 3.69GB 2/9  ->  t04 31.6%  ->  t05 32.1% 32.1%
```
即 `bytes` 在 8.31 GB 与 3.69 GB 之间来回，`filesDone` 从 5 掉回 2 —— 是**真回退**，不是渲染。
旁证：
- 计划文件里标 `pending` 的三个文件，磁盘上正有 `.partial` 在长（348 MB / 94 MB / 76 MB）；
- 日志里同一批文件在 `16:23:53`、`16:37:11`、`16:38:31`、`16:59:43` 被反复 `event=copy`；
- 目录里已有 1.8 GB《Two girls play》和 2.3 GB《alone in room》，计划里却又成了 `running / attempts=0`。

### 根因
`_start_safe_dir_job` 撞见旧线程时只做 `old["stop"].set()`，紧接着就把 `SAFE_JOBS[id]` 换成新的 `Event`。
而工作线程判停是 `_safe_requested_stop(job_id)` —— 按 job_id 去查 `SAFE_JOBS` 的。
**换掉 Event 之后，旧线程永远看不到那个已置位的信号**，于是它把自己手上那套 entries 一路跑到底；
新线程又从另一个基线（重新扫描后的计划）开始算，两代交替写同一个计划文件、同一个 `bytes`，
进度就来回升降。前端进度条还有 500 ms 缓动，回退过程更显眼。

### 改动（v4.17）
- 重复启动时：置旧信号 → `stop_job_group()` 取消在飞 job → `join(SAFE_RESTART_WAIT=8s)` 等旧线程真正退出
  → 才换新 `Event` 起新世代；
- 8 秒还没退出就拒绝启动，`resume` 把原因回给界面，不再出现「已暂停」被当成功；
- 新增 `tests/test_restart.py` 两项：旧线程会退时只留一个世代 / 旧线程卡住时拒绝启动。

### 验证
- 测试 **337 项 OK，1 skip**；部署 v4.17（MD5 `9ab07e2d1f9bd666bf1c8d7c9792a00e`，备份 `.bak-v416`），
  恢复两个任务后连续 2 分钟采样，`bytes` 单调递增、无一次回退。
- 提交 `2a199cd`，Release v4.17。
