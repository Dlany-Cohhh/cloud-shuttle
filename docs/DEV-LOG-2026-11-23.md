## 三、速度：两个真问题，不是账号限速

### 3.1 诊断过程

先用对照实验排除「账号被限速」「配置写错」：同样的账号、同样的 16 连接，只是换文件组合，速度就差一个数量级。真正的原因是**并发槽被几个 0.01~0.02 MB/s 的文件长期占住**：4 个槽里有 2 个在等「永远下不完」的慢文件。

### 3.2 v3.95 龟速让位

- `stallSeconds` 成为设置项（默认 90 秒，原来硬编码 300 秒），判定阈值仍是 50 KB/s；
- 让位过的文件打 `slow` 标记，第二轮进「慢速尾池」，不再抢主池；
- 尾池加 `slow_tail_hopeless()` 兜底：30 分钟推不动 1 MB 即判 `hopeless` → `failed`，保证任务能收尾。

实测（四路并发，同一账号）：

| 阶段 | 速度 MB/s |
|---|---|
| 改动前 | 0.60 / 2.04 / 2.58 / 2.29 |
| 改动后 | 7.67 / 7.20 / 10.41 / 12.08 |
| 中段（15 分钟窗口） | 10.27 → 15.24 |

### 3.3 v3.96 尾池按连接预算开槽

v3.95 的尾池固定 1 个槽，收尾段把 16 连接用成了 4 条，实测掉到 0.28~0.37 MB/s。
改为 `tail_workers(s, workers) = min(任务并发, AUTOTUNE_MAX_CONNS(16) / multiThreadStreams)`，4×4 时用满 4 个槽：

| 场景 | 速度 MB/s |
|---|---|
| 收尾段（1 槽） | 0.70 |
| 收尾段（按预算 4 槽） | 1.27 |
| 随后恢复段 | 1.94 → 11.85 |

最终 157/159 → 159/159 跑完。

### 3.4 三条可复用的结论

1. **16 连接是服务端硬上限**：24/32/64 连接会塌一个数量级，不是「越多越快」。
2. **同样 16 连接，摊到更多文件更抗慢文件**：慢文件只污染它自己那一路，不再拖住整个任务。
3. **`core/stats.speed` 会重复计被取消重试的字节**：唯一可信口径是目标目录的真实落盘增量。这次所有提速数字都是按目录增量口径量的。

## 四、一致性校验（v3.97）

### 4.1 现象

点「一致性校验（快速·清单+大小）」后红字报错：

```
云端连接失败：Command 'docker','exec','rclone-backend','rclone','lsf','--stat',…
timed out after 60 s
```

### 4.2 两个独立根因

1. **`--stat` 对「目录」在 PikPak 上永不返回**。我手工在 NAS 上跑同一条命令：25 秒超时、零输出。旧版每次目录校验都先做这一步，等于固定白等一个超时，然后被判「云端连接失败」。
2. **安全命名截断造成假缺失/假多余**。开了安全命名后超长文件名被截断成 `原名~hash.mp4`，校验按名字直接配对，同一份文件同时进「本地缺失」和「本地多余」——实测当时报 `match 149 / missing 10 / extra 10`，但两侧都是 159 文件、241,953,030,215 B。

### 4.3 修法

- `rename_map_for(remote, cloud_path, local_root)`：读安全命名清单 `.cloudshuttle-name-map.json`，把云端原名翻成落盘名再比对；
- `pair_renames_by_size(items)`：清单没覆盖到的（历史任务、更早版本落的盘）按「某大小恰好 1 缺失 + 1 多余」唯一配对，配成 `renamed` 并丢弃本地那条（`_merged` 标记），避免条目翻倍；
- 新增状态 `renamed`（界面「改名一致」），「只看差异」筛选把它视为一致；
- **去掉 `--stat` 首探**：直接递归列一次，用返回值自己判断单文件（只列出一条且 `Path` 恰是请求的最后一段文件名）；
- 列目录「首次 60 秒 + 立刻重试一次 150 秒」：PikPak 的耗时是双峰的，实测 04:32 挂满 150 秒失败、04:34 同参数 1.2 秒返回 159 条；
- 前端 `verify` 请求上限 120 → 300 秒（否则服务端还在重试，浏览器先自己 abort）。

### 4.4 实测

| 版本状态 | 耗时 | 结果 |
|---|---|---|
| 旧版（含 12 秒 stat 首探） | 13.7 秒 | ok=True，但每次白等一个首探 |
| v3.97（死守旧逻辑那次） | 108.9 秒 | ok=True |
| v3.97 去掉首探后 · 第 1 次 | **1.4 秒** | ok=True，attempts=1 |
| v3.97 去掉首探后 · 第 2 次（赶上抖动） | 122.2 秒 | ok=True，attempts=2，界面提示「第 2 次才成功」 |

四次的清单结果都是 `total 159，match 134 / renamed 25 / missing 0 / extra 0 / size 0`，两侧字节完全一致。

### 4.5 踩坑记录

`_name_map_path()` 要的是 `{"console": <卷根>}` 这样的 dict，不是字符串。第一版传了字符串，`AttributeError` 被吞掉，映射为空，于是「没有找到安全命名清单」，退回按大小配对——现象看起来像「清单功能没生效」，其实是参数类型错。

## 五、列表轮询超时（v3.98）

### 5.1 现象

界面经常弹：`后端服务连接失败：请求超时（8 秒），源端可能无响应 —— 每 2 秒自动重试`。

### 5.2 机制

这不是后端挂了，是前端自己的看门狗：页面每 2 秒拉一次任务列表 `jobs`，单次请求超过 8 秒就点亮红条，下一轮成功即消失。

### 5.3 根因

`jobs` 处理**整段持有全局锁 `LOCK`**，里面每个「运行中」任务还要串行问 rclone 两次（`job/status` + `core/stats`，各 8 秒上限）。两三个任务一叠加就是 30 秒以上；这段时间锁一直被占着，连「停止」「保存设置」都得排队。

### 5.4 修法

- 全局锁只在读 `jobs.json` / 写 `jobs.json` 的瞬间持有，`job_live` 移到锁外；
- 写回改成「按 id 合并进度字段」（`bytes/total/speed/eta/files/curfile/phase/transferred/_xf/_miss/_mapState/filesDone/filesFailed`），`state` 只在目标仍是 `running/queued` 时才跟着变——用户刚点「停止」不会被迟到的查询改回运行中；
- 单次 rc 超时 8 → 4 秒，整轮预算 6 → 4 秒；
- 1.2 秒内的重复轮询直接复用上一份结果（多标签页、一秒一刷不再重复打 rc）；
- 服务端新增慢请求日志：任何动作超过 2 秒打一行 `慢请求 <action> N 秒`；
- 前端红条改为**连续 2 次失败才显示**，并带上「已连续 N 次」。

### 5.5 实测

| 测试点 | 结果 |
|---|---|
| NAS 本机连打 10 次 `jobs`（空闲） | 每次 **10~20 ms** |
| 从 Windows 走 HTTPS 打 12 次 | **26~41 ms** |
| 容器内线程数 | 3（无泄漏） |
| 重启后 `consoleVersion` | v3.98 |

也就是说空闲链路完全正常——旧版只在「有任务在跑」或「锁被慢操作占着」时才超时。这次改动后即使有任务在跑，列表请求也不再排长队；若还弹，就看容器日志有没有「慢请求」：没有就是链路侧的抖动，有就继续优化那条路径。

## 十一、补记（v4.01，同日）：分账号下载

第八节遗留问题 2「多账号分片仍不可用」这次从**能力**上解决了 —— 但它是**工具缺失**，不是账号数据问题：
在此之前程序里根本没有「一个目录拆给多个账号」的入口，只能手工给每个账号建任务、再靠过滤规则勉强划分。

新增 `splitscan`（只读预检）与 `splitstart`（按文件建 N 条分片任务），要点：

- **字节均衡**而不是文件数均衡：LPT 贪心，大文件先给当前累计最少的账号。按文件数分会让某个账号早早跑完干等。
- **集合一致性是硬门槛**：只有所有账号的「路径 + 大小」完全相同才允许开始。分给 A 的文件 B 没有，任务必然失败；
  预检用**并集**算缺口（「这个账号少了别人有的东西」），交集口径下 `missing` 恒为 0，报错方向是反的。
- **落点统一**：分片不走 `dedupe_dest`，否则第二片会被改成「目录-2」，一份资源被拆进两个文件夹。
- **过滤只算一次**：拆分前用 Python 按 rclone 规则语义过滤，分片任务只带 `fileList`、不再注入 `_filter`。
  两套语义（Python 侧大小写不敏感、rclone 默认敏感）会让「分到的文件悄悄不下」，这是最坏的一类 bug。
- **校验要认别账号的落盘名**：安全命名哈希输入含账号名，分账号下载后同一目录混着多个账号的名字，
  单账号校验会把它们同时报成缺失 + 多余。新增 `rename_alias_map`，按相对路径聚合所有账号的映射做别名。
- **不受 `maxConcurrent` 限制**：同源分片排队就完全失去了并行的意义；每片仍是独立账号、独立连接预算。

实测依据（本轮，只读）：`operations/list` 用 `fs=账号:目录, remote=""` 时 `Path` 是**相对该目录**的，
目录条目 `Size=-1`；目录不存在返回 `error in ListJSON: directory not found`（HTTP 404 + 200 混合语义），
`_strict=True` 会抛异常 —— 因此预检把「目录不存在」单独判成「还没转存」，而不是故障。

**当前线上仍不具备真实多账号分片的条件**：`存储1-new` 只有 `会员号` 有，`pik-1` 直接是 `directory not found`。
要真正跑起来，先把该目录用「跨账号转移」（relay，不消耗下载配额）复制到其它账号，再预检。

## 十二、实测：真实分账号下载跑通（v4.01 部署后当晚）

第十节说的「线上不具备多账号分片条件」，本轮用一份自造小资源补上了对照实验：

- 源：`/vol2/Data-storage/.cs-split-src` 下 4 个随机文件，6 / 4 / 3 / 2 MiB，合计 15,728,640 B。
- 三个账号（`会员号` / `pik-1` / `pik-3`）各放一份完整副本（跨账号分享转移在本区不可用，
  `xferstart` 报 `Share Unavailable in Your Region`，改用 `rclone copy` 直传，对本实验等价 —— 预检只要求集合一致）。
- `splitscan`：`consistent=true`、`fileCount=4`、`bytes=15728640`，分配 2/1/1 片，
  字节 5,242,880 / 6,291,456 / 4,194,304。
- `splitstart`：3 条任务同一 `dest=/data/Downloads/分账号测试`，`split.group` 相同、`index` 1..3。

结果（全部实测，不是推断）：

| 检查项 | 结果 |
| --- | --- |
| 三片是否并行 | 是。`maxConcurrent=2` 却三片同时在跑，说明 `split_peer_running` 旁路生效 |
| 落点是否同一目录 | 是。`/data/Downloads/分账号测试`，没有出现 `-2` 后缀 |
| 文件是否互不重叠 | 是。`{C,D}` `{A}` `{B}`，并集 4 个 |
| 字节是否对上 | 是。5242880 / 6291456 / 4194304，`filesFailed=0` |
| md5 是否一致 | 4 个全一致（源与落盘逐个比对） |
| 残留 | 无 `.partial` / `.tmp` |
| 一致性校验 | 三个账号分别 `verify` 都是 4/4 match、0 missing / 0 extra |

两个只在真机上才看得到的细节，记下来免得下次又当成 bug：

1. **先看到 `event=copy`、再看到目录**是正常时序 —— 分片任务开跑那一刻目标目录还不存在，
   `ls` 会报 `No such file or directory`；rclone 建目录发生在第一个文件真正开始写之后。
   这次误判过一次，实际只是查得太早（约 10 秒）。
2. 落盘文件属主是 `root:root`、模式 `0745`（rclone-backend 以 root 跑）。组内可读、其他人可读，
   控制台（uid 1000）读没问题；但 NAS 普通用户**改不了删不掉**。这是既有行为（`存储1-new` 一样），
   不是 v4.01 引入的；要改得给 rclone-backend 加 `PUID/PGID` 或写 `--uid/--gid`。

速度方面没有惊喜也没有回退：15 MB 花了约 90 秒，与前面「无速度」事故里定性的 PikPak 限速一致，
不是分片逻辑的开销（三片各走独立账号、独立连接预算）。

## 十四、v4.03：慢的根因不是限速，是连接僵死（同日晚）

用户第二次问「为什么速度还是这么低」，截图里两个任务 74 KB/s 和 59 KB/s，剩余 495 / 928 分钟。
上一轮我给的结论是「国际链路只有几十 KB/s，贴近上限」——**这个结论是错的**，这一轮被实测推翻。

### 14.1 怎么推翻的

先按「链路」方向排查，全部排除：

| 观测 | 结果 | 排除了什么 |
| --- | --- | --- |
| 磁盘 `dd` 到 /vol2 | 116 MB/s | 磁盘 |
| 国内下载（清华源） | 17.8 MB/s | 家宽下行 |
| 日本 / 新加坡直连 | 53 / 135 KB/s | 「国际出口整体很差」有可能，但不解释下面这条 |
| 同节点 `pik-3` 单流 | 448 KB/s | 节点本身 |
| TCP 重传率（10s 采样） | **0.00%** | 丢包 |
| 到 CDN 建连 RTT | 293~471 ms | 极端绕路 |

关键转折是「停一下再继续」这个动作。为了验证「两个任务是不是共享账号额度」，我停掉了一个：

- 停掉后剩下那个 **还是 58 KB/s** → 不是共享额度，各跑各的；
- 再 `stop → resume`，它立刻变成 **8.9 MB/s**；另一个也 resume，变成 **23.4 MB/s**。

同一账号、同一文件、同一分钟，唯一变化是「换了一条新连接」。所以废掉的是连接，不是配额。

### 14.2 为什么 stuckWatchdog 没管

`_stuck_watchdog`（v3.83）的判据是「字节完全不动 **且** 速度为 0 **且** 没有在传文件」。
僵死连接的形态是第三种：**字节还在涨，只是只有几十 KB/s**，速度字段非零 —— 三条都不满足，
于是它一路静默，任务就这么挂着跑几十小时。

### 14.3 做法

新增 `_reconnect_watchdog`：按「窗口内平均速度」判定，低于阈值就自动 `stop → 重新排队`。

用**均值**不用瞬时值：同一文件实测 10 秒内从 204 KB/s 掉到 16 KB/s，瞬时值判据必然误杀。
窗口默认 180s、阈值 384 KB/s；每踢一次窗口翻倍（180→360→…→3600），最多 5 次。
翻倍 + 封顶是给「真的只有几百 KB/s」的线路留的余地：不会无限次丢掉半截 `.partial`。

### 14.4 真机抓出来的两个 bug

1. **基线不落盘**。调度器只在 `changed` 为真时 `save_jobs`，而「记基线」这一支返回 False，
   于是下一轮从 `jobs.json` 读回的 `_kickAt` 还是 0，`not base_t` 永远成立 ——
   看门狗永远停在第一步，一次都不会触发。改成「job 被改过就返回 True」。
   这条只有真机才看得见，单测里 job 字典是同一个对象，永远不会回读。
2. **拿字节回退当变慢**。线上任务字节从 736 MB 掉回 161 MB（任务自己重启、重算进度），
   被当成「更慢」踢了一脚。改成 `cur < base_b` 时只重记基准。

两个 bug 各留了一条回归测试，并在注释里写清了现场数据。

### 14.5 真机验证

部署后把阈值临时抬到 8 MB/s、窗口 60s，线上任务按时触发：

```
2026-11-23 12:46:42 [job 1795436550509] event=reconnect rate=219 kick=1/5 win=60
```

窗口自动翻倍到 120s，任务重新排队。用回默认阈值（384 KB/s / 180s）后：

- `会员号:存储1-new`（原显示「剩余 495 分钟」）→ **10 分钟内下完**，2.28 GB / 2 文件 / 0 失败
- `会员号:存储1-new/悠米`（原显示「剩余 928 分钟」）→ 下完，3.16 GB / 1 文件

## 十五、v4.04：不是「转不出 mp4」，是 PikPak 给的就是 MPEG-TS（同日深夜）

### 15.1 现象与误判

用户发截图说「下载的文件不能转化为 mp4」。第一反应是怀疑我们的安全命名把扩展名吃掉了
（目录里确实一堆 `~6389f075a6aa` 这样的尾巴）。但翻开 `.cloudshuttle-name-map.json`，
`original` 字段里 PikPak 的真实文件名**本来就没有扩展名**：

- 有扩展名：`…#闪闪工作室 我用气球玩弄帝国军女俘虏.mp4`
- 没扩展名：`…#悠米…极光白丝`、`…#绳缚日本「Twins」…巅峰之上还有巅峰！`

所以哈希后缀只是我们去重用的，和扩展名无关。真正的原因是容器：

```
head -c 96 file | od -A d -t x1z
0000000  47 40 11 10 ... 46 46 6d 70 65 67 20 53 65 72 76 69 63 65 30 31
          G  @  .  .      F  F  m  p  e  g     S  e  r  v  i  c  e  0  1
```

`0x47` 是 MPEG-TS 的同步字节，`FFmpeg Service01` 是 ffmpeg 的 ts 复用器写进去的服务名 ——
PikPak 上这些资源是 HLS 切片拼出来的裸 TS，连扩展名都没给。

### 15.2 为什么是「转封装」而不是「转码」

`ffprobe` 报 H.264 1080p + AAC，正好是 MP4 的原生组合，所以 `-c copy` 就够：

| 指标 | 源 TS | 产物 MP4 |
| --- | --- | --- |
| 体积 | 1,902,391,176 | 1,753,166,641（**-7.8%**） |
| 时长 | 3471.700000 | 3471.700000 |
| 耗时 | — | 34 秒 |

体积变小是去掉 TS 的 188 字节包开销，不是重编码。抽帧验证 `-ss 600` 能正常出图。

### 15.3 批量补转时踩到的 shell 坑

第一版脚本用 `find -print0 | while read -r -d ''`，busybox 的 `read` **不支持 `-d`**；
退回 `find | while read -r` 后，又有一个文件名里带**换行符**，被拆成三行，
于是出现 `START 行` / `Error opening input file 行.` 这种日志。最终改用
`find ... -exec sh -c 'for f do … done' _ {} +`：名字原样从 `$@` 进 `for`，换行空格都不怕。

另外 13.6 GB 的批量转换放在同步命令里跑，**会话 120 秒超时把它砍了**，
留下一个 745 MB 没有 `moov` 的残缺 mp4。改成 `nohup … &` 起后台脚本、日志写文件，
才不受工具超时影响。

### 15.4 那个「转不出来」的文件其实是坏的

`悠米/#悠米…6389f075a6aa`（3.39 GB）转 34 分钟只出 745 MB 就卡死，日志：

```
[in#0/mpegts] max resync size reached, could not find sync byte
```

抽样读盘才看清：**0.75 GB → 3.2 GB 整段是零**，而且 `du -b` 等于 `du -b --apparent-size`
—— 不是稀疏文件，是实实在在写进去的零字节（那次下载正好是被 captcha 风控挂住的任务）。
`ls -l` 尺寸对、`ffprobe` 也能读出 2792 秒（尾部数据是好的），所以任何「只看尺寸」的校验都发现不了。

结论：这个文件只能重新下载。代码侧加了两道闸，避免再把坏文件转成「看起来能播」的半成品：

1. 转前 `zero_holes()` 抽 9 个位置、每处读 200 个 TS 包，整窗全零就判「需要重新下载」；
2. 转后比时长，产物短于源 98% 就删掉半成品、保留源文件。

### 15.5 ffmpeg 从哪来

容器是 `python:3.12-alpine`，原来只有 `docker-cli`。宿主机那个 `/usr/bin/ffmpeg` 是
`/usr/trim/lib/mediasrv/ffmpeg` 的软链，glibc 编译的，搬进 musl 容器跑不起来。
所以：`Dockerfile` 加 `apk add ffmpeg`（下次重建镜像自带），运行中的容器就地 `apk add` 一份。
顺带把 `ffmpeg_bin()` 的负缓存从「永久」改成 60 秒 —— 否则先起服务后装 ffmpeg 的进程
会一直记着「没有」，只能重启。

## 十六、v4.06：卡在 97.4% 的真相 —— 源端没有直链，而看门狗把它变成了死循环（11-24 上午）

最后一个文件 `32【Chrisgag】…壁虎女….mp4`（1.71 GB）已传 0 字节、速度 0，

### 16.2 三层证据都指向同一个结论

2. **看门狗与单文件重试在赛跑**：v4.03 的看门狗 180 秒就 `stop → 重排队`，

- `SOURCE_DEAD_KEYS` → `FILE_FATAL`，不重试，提示语点名「PikPak 侧文件未就绪或已损坏，需重新转存」；

## 十七、v4.07 / v4.08：`operation not permitted` 的两个层次（11-24 上午）

### 17.1 先按报错路径去查，别按截图猜

用户截图里一行红字：

```
rc job/status: open /data/#Chrisgag xxx.mp4.7fefa8fb.partial: operation not permitted
```

第一反应是权限 / 磁盘满。逐层排除：

| 检查 | 结果 |
| --- | --- |
| `docker inspect rclone-backend` 挂载 | `/vol2/Data-storage -> /data`、`/vol3/downloads -> /vol3/downloads`，`RW=true`（易读反） |
| 容器内 `touch /data/x` | 报 EPERM，**但文件被建出来了**，0 字节 |
| 容器内 `touch /vol3/downloads/x` | 成功，能回读内容 |
| 宿主 `echo hi > /vol2/Data-storage/t1.txt` | 同样 EPERM，0 字节 |
| `findmnt -T /vol2/Data-storage` | 不在任何卷上，落在 `/dev/sdb2`（55 G 系统盘） |
| `ls /vol2` | 空壳，`du -sh` 只有 20K；旧数据不在里面 |

结论：`/vol2/Data-storage` **已经不是卷**，是换盘后留在系统盘上的残留目录，
两个容器的 bind 还指着它。它的「半可写」最致命：建文件能成，写数据 EPERM，读也 EPERM——
所以 `df` 有空间、目录存在，程序一路绿灯。

### 17.2 v4.07：把「可写」当门槛，而不是假设

旧逻辑按「rclone 侧 `/data` 优先」排序，正好把假卷排成主卷，新任务 100% 落进去。
新版 `volume_writable()` 真写 4 字节 + `fsync` 才算可写（120 秒缓存，卷修好后自动恢复），
`storage_pairs()` 改成可写优先，`start` / `urldl` 直接拒绝不可写卷，报错点名根因。
`DISK_FATAL_KEYS` 也补上 `operation not permitted`，这类错误不再被当成瞬时抖动反复重试。

上线后线上立刻翻转：

```

存储空间 2 /data          -> /vol2/download  | free 39.2  | w False
```

### 17.3 v4.08：修好卷之后，第二个缺陷显形

任务换成 `/vol3/downloads` 后能下了，但落点不对——1.71 GB 的成品躺在卷根，
和 49 个兄弟不在一起。回头看卡片：`目标 /data/Downloads/#Chrisgag xxx.mp4`，
而 rclone 报的是 `/data/#Chrisgag xxx.mp4.partial`，**少一层 `Downloads`**。

单文件任务在未指定 folder 时 `dst_dir` 直接取卷根，`copyfile` 就往卷根写；
卡片上的 `dest` 用的是另一套拼法。两套路径从来没对上过，因为单文件任务此前
一次都没成功落过盘（唯一的尝试正好撞在假卷上）。

改法（`single_file_dst_dir()`）：未指定 folder → `卷根/Downloads/<源文件所在文件夹名>/`，
`dest` 统一改成 `dst_dir + 落盘名`，并在 `launch_job` 里先幂等建目录。

### 17.4 真机验证（不靠「应该好了」）

1. 重建任务到 `/vol3/downloads`：3.7 MB/s × 321 秒 → `done`，1,634.8 MB；
2. 落盘 `1,714,254,758 B`，与源端字节数一致，头部 `00 00 00 20 66 74 79 70 …`（`ftyp isom`，标准 MP4），
   不是 TS，无需转封装；
3. 移入 `Downloads/Chrisgag/`（50 个文件）；
4. 用 v4.08 对同一源再建任务：`dst_dir = /vol3/downloads/Downloads/Chrisgag`，
   `dest` 与真实路径一致，rclone 判定「目标已存在相同文件」直接跳过（0 字节传输）。

## 十八、v4.09：1 号盘接入（11-24 上午）

### 18.1 用户的要求与物理现实

用户提出：系统盘"只用 20 G 就够"，想把省下的 20 G 和 `/vol1` 合并进云梭。
先把账算准（512 字节扇区）：

| 分区 | 起点 | 大小 | 终点 |
| --- | --- | --- | --- |
| sdb1 (EFI) | 2,048 | 192,512 | 194,559 |
| sdb2 (/) | 194,560 | 116,992,000 | 117,186,559 |
| sdb3 (md0→/vol1) | 117,186,560 | 117,254,144 | 234,440,703 |
| 磁盘末尾 | — | — | 234,441,648 |

三条硬约束让这个方案不成立：

1. **零空隙**：`sdb2` 终点与 `sdb3` 起点紧邻，磁盘尾只剩 944 扇区（约 460 KB）；
2. **ext4 不能在线缩容**：`resize2fs` 缩容必须卸载文件系统，而它就是运行中的 `/`；
3. **分区只能向后长**：即使离线缩了 `sdb2`，腾出的空隙在 `sdb2` 与 `sdb3` 之间，
   `sdb3` 的起点固定，接不上 —— 只能另立分区，合并不了。

要真合并，只能 U 盘启动 → 备份 `/vol1` → 删 `sdb2`/`sdb3` → 重建 → 重装飞牛 → 恢复容器与数据。
为 20 GB 重装一台 NAS，不划算；而且 `/` 现在 55 G 用 13 G，缩到 20 G 只剩 7 G 余量，
飞牛更新、Docker 镜像层、容器日志都在上面，写满即全挂。

### 18.2 改走「挂载现有空闲」的路

`/vol1`（飞牛的「存储空间 1」）还有 49.5 GB，实测容器内写入 243 MB/s。
不动分区，给两个容器各加一条 bind：

```
rclone-backend   + -v /vol1/downloads:/vol1/downloads
download-console + -v /vol1/downloads:/vol1/downloads
```

程序靠「两个容器宿主路径相同的挂载点」配对识别存储空间，所以两边都要挂、路径必须一致。

重建前把两个容器的完整 `docker inspect` 存到 `/vol1/docker-apps/_rebuild_backup/`，
旧容器 `docker rename` 成 `dc-old-409` / `rb-old-409` 保留作回滚点（未删）。
参数照抄：host 网络、`restart unless-stopped`、日志轮转 100m×5、工作目录、环境变量。

### 18.3 顺序问题：小盘差点成了默认落盘卷

`rank_pairs()` 原来同可写时按路径字符串排，`/vol1/downloads` < `/vol3/downloads`，
而「新建任务不指定卷 = 取第一个」—— 50 GB 的系统副盘会变成默认下载盘。
改成**总容量大的优先**：

```python
pairs.sort(key=lambda p: (not p["writable"], -int(p["capacity"]), p["rclone"]))
```

用总容量而不是剩余空间，是因为容量不随下载进度变化，「存储空间 N」的编号才不会跳。

顺带修掉 v4.07 的一个缓存 bug：可写性只在首次识别时探一次就存进 dict，
注释里写的「两分钟自愈」其实要重启才生效。现在每轮重排都重探（底层 120 秒 TTL）。

### 18.4 验证

```
存储空间 2  /vol1/downloads -> /vol1/downloads   55.9G  剩  49.5G  可写
存储空间 3  /data           -> /vol2/download    54.6G  剩  39.1G  不可写
```
