## 四、关键技术决策与根因

1. **多卷识别用挂载配对而非配置文件**：`docker inspect` 比对两个容器的宿主 `Source`，避免让用户手填卷列表；代价是强依赖 `docker.sock`，因此保留单卷回退路径。
2. **目录大小三阶段演进**：`rclone size` 递归 → PikPak 原生 API（优先信文件夹自带累计 size）→ 进目录自动统计。核心取舍是「零递归优先、按需下钻」，再加并发上限、缓存、超时、条目数四重保护，避免一次进目录打爆接口。
3. **前后端版本一致性**：单页应用不刷新就跑旧 JS，是新后端最常见的「假 bug」。用 `state.version` 主动感知 + 请求序号防竞态，比让用户清缓存可靠。
4. **双 rcd 进程是多个账号问题的共同根因**：删除后复活、改名后旧名重现，都源于 5572 / 5573 各持一份内存配置，任一次保存会写回另一份的旧内容。所有账号写操作必须双进程对齐。
5. **`pkcollect://` 只写 HKCU**：用户级注册表、可卸载，不需要管理员权限，也不改动默认浏览器关联。
6. **前端条件渲染必须是完整链**：`v-if` 混用导致内容串扰，是 v3.69 冗余感的真正原因，删文案解决不了。

### 冒烟发现并修复的两个真 bug

**BUG-1 · `dirsize` 回退路径崩溃（用户长期反馈「文件夹大小显示不出来」的残留根因）**
`dirsize(My Pack)` 在原生 PikPak API 抛异常后进入兜底，报 `cannot unpack non-iterable CompletedProcess object`。原因：`_rclone_run()` 返回的是 `subprocess.CompletedProcess`，而 4704 行写成 `code, out, err = _rclone_run(...)`。修复为 `p.returncode` + `_decode(p.stdout / p.stderr)`，并保留原生异常文本进错误信息。现在兜底成功返回字节数、失败返回明确 error、非法 JSON 返回明确 error，三条路径都有离线用例。

**BUG-2 · docker.sock 不可用时回退失效（隐藏缺陷，当前部署未触发）**
`LEGACY_VOLUME` 没有 `host` 键，而 `refresh_storages()` 用 `p["host"]`，一旦 `storage_pairs()` 走回退分支就 KeyError，存储空间列表与容量刷新全废。修复：`LEGACY_VOLUME` 补 `host: ""`，取值改 `p.get("host", "")`。离线用例模拟 docker.sock 异常 + 无 host 的旧格式 pair，验证不再抛错且容量正常计算。

**UI 调整**：按用户截图要求，把「导入 / 采集 Token」按钮从独立第二行移到「类型下拉 + 账号名」同一行的最右（`ml-auto`），且仅在 PikPak 方式显示；下方只保留流程说明。

## 十、v3.73：文件夹大小统计体验优化（2026-11-13）

**现象**：真机云盘预览根目录 10 个文件夹，1/3/4/5/6 显示 GB，2/7/8/My Pack/Pack From Shared 显示 `--`。

## 十五、v3.78：修复「代理」按钮点击无反应（2026-11-13）

**现象**：用户升级到 v3.77 后，代理地址已填 `https://127.0.0.1:7890`，但点「代理」按钮毫无反应（无 toast、无切换）。真机 `settings` 确认 `netMode=direct`、`proxyUrl=https://127.0.0.1:7890`。

**根因**：`proxyAddrValid` 定义在 `static/app.js` 的 `computed:` 块（286 行起），而 `setNetMode` / `applyProxySuggestion` 在 `methods:` 块（801 行起）。Vue Options API 会把 computed 自动解包成值，`this.proxyAddrValid` 是布尔值而非函数，`this.proxyAddrValid()` 抛 `TypeError`，事件处理在第一行就中断，因此表现为「按钮点不动」。v3.77 的离线测试把 computed 与 methods 混在普通 JS 对象里执行，掩盖了这个差异。

## 十六、v3.79：本地文件点播放全部黑屏（2026-11-13）

**现象**：本地文件页点任意视频，弹窗里只有一块黑底 + 控制条，时间停在 `0:00`、没有总时长、没有缓冲圈、没有任何提示（用户描述「像一张图片，没有任何播放」）。截图文件为 `11466.mp4`（665.7 MB，`/vol2/download/3/kz`）。

**排查过程**：
1. `version` 回 `v3.78`、`https: true`；`localfiles` 返回的 `kind=video`、`playable=true` 都正常。
2. 怀疑「moov 在文件末尾（非 faststart），浏览器要下完整个文件才出画面」。取头部 box 链核对：`11466.mp4` 与抽样的小文件都是 `ftyp(32) → moov(...)`，`moov` 在**头部**，排除该假设。
3. 直接压 `/media/` 的 HTTP 层：`200/206` 正确，`Content-Type: video/mp4`、`Accept-Ranges: bytes` 齐全；17 MB 文件全量 0.73 s（24 MB/s），`bytes=-2048` 尾块 0.02 s，https 与 Range 组合也正常 → 服务端传输没问题。
4. 对比两种 URL 形式，差异立刻显现：
   - `/media/3/kz/11466.mp4` → `206`
   - `/media/vol2/download/3/kz/11466.mp4` → **404**
   而前端 `lfUrl()` 拼的正是后者。

**根因**：`do_GET` 里 `rel = path[7:]` 把 `/media/` 连同斜杠一起去掉，剩下的 `vol2/download/3/kz/11466.mp4` 不再以 `/` 开头，`safe_local_path()` 于是走「相对主卷」分支，拼成 `/vol2/download/vol2/download/3/kz/11466.mp4`。v3.57 把本地页导航改成控制台绝对路径后，前端一直传绝对路径，后端却按相对解释 —— 两边约定错位，**所有本地文件 404**。同一批坏链接还波及列表「下载」、播放器「下载到本机」和 M3U 导出。

**修复**：
- 新增 `media_local_path(rel)`：若 `<rel>` 以某个卷的控制台根开头（去掉前导斜杠后比较），补回前导 `/` 再交给 `safe_local_path()`；否则维持「相对主卷」老语义。绝对路径、老的 `/media/1/喵兔/x.mp4`、多重前导斜杠都兼容，`../` 越界仍被拒绝。
- `_serve_media()` 改用该函数。
- 前端 `onPlayerError`：本地文件原先第一行就 `return`，失败无声。现在按 `MediaError.code` 给出可读原因并提示「下载到本机」。

**顺带精简**：按用户要求，「进阶设置」折叠只保留「代理地址」格式一句，其余四段（守护进程 / 仪表盘测速 / 他人部署）删除；`socks5://` 的生效范围改成填了 socks5 才提示；缺地址时用 `focusProxyUrl()` 把光标放进地址框，替代原先"自动展开说明"。

**验证**：`test_v379.py` 20 项全部 PASS（路径归一化、副卷、老链接、越界、路由接线、前端静默修复、Range 未回归）；`python -c "ast.parse"` 与 `node --check` 均通过。

**给后续的教训**：凡是由前端拼 `/media/`、`/thumb` 这类前缀路由的地址，后端必须同时接受「绝对路径」与「相对主卷」两种写法，否则 v3.57 这种导航改造会静默打断所有媒体链接 —— 而 `<video>` 的失败又不会冒泡成可见错误。

**做法**：不靠"看起来没问题"，而是三路并行取证 ——

3. **换环境推演**：逐条问"用户不按我们的 compose 来会怎样" —— 仓库放到别的目录、不给

## 十七、v3.81：云端文件夹三态 + 完整 CRUD / 多选拖拽（2026-11-14）

用户提了两个功能点，动手前先用 4 个问题把口径钉死（避免做完返工），选定：
**本地文件逐项比对判定 / 「有更新」手动确认才消失 / 本地删除进可恢复回收站 / 发 v3.81 并升级 NAS**。

**功能 1 的设计要点**：`dirs` 的注释里原本写着「目录不打标（要判整个目录都下过，得递归
列云端，太重）」。这次没有把这个判定塞进 `dirs`，而是独立成 `folderstatus` 异步接口 ——
列表照旧秒开，进目录后再补状态，用 `_dirsSeq` 丢弃切目录前的过期响应。

最难的不是「下完了没有」，而是**「有更新」相对谁而言**。没有基线就无从判断"新加入"。
所以持久化一份 `seen = 最后一次判定完毕或用户确认时的云端文件签名集合`（相对路径|字节数），
`added = 当前集合 - seen`。关键推论：云端加新文件后本地必然还没下完，如果按「是否全部下完」
来显示，标识会闪一下就没了 —— 所以 `added>0` 时无条件显示「有更新」，与本地补齐与否无关。
用户点确认只推进 `seen`，不伪造下载状态：补齐了回「下载完毕」，没补齐就退回无标识。

**踩到的一个隐蔽坑**：本地回收站的索引要落 JSON，而 `_fs_name()` 存在的意义就是磁盘上可能
有孤立代理字符（Windows 拷入的 GBK 名）。这类名字进 manifest 会让 `_write_json` 抛
`UnicodeEncodeError`，而此时文件已经被移走了 —— 索引写不进去，等于条目凭空消失。
处理：删除前检测 `_fs_name(real)[1]`，命中就拒绝并提示先用铅笔重命名。
不为了兼容一个坏名字去把整条索引链路改成 base64，保持简单比"什么都能处理"更重要。

**另一个取舍**：云端新建文件夹原本打算用 rc `operations/mkdir`，但查文档没拿到权威的
参数说明；项目里已经大量使用 `rclone_cli()` 且 `rclone mkdir remote:path` 是确定的 CLI 命令，
于是换成 CLI，与 `cloudmove` 的 `moveto` 走同一条通道。`pikpak` 有 `DirMove`，目录移动是
服务端操作，不会真的下载再上传。

**前端**：新增 17 个 methods / 2 个 computed；列表与缩略图两种视图都挂了拖放事件，
「返回上一级」也做成 drop 目标（移出当前目录很常用）。徽标里那个可点的「有更新」最初写成
`<button>`，但外层已经是 `<button>` —— HTML 不允许按钮嵌套，Vue 编译后 DOM 会错乱，
改成 `role="button"` 的 `<span>`，并在测试里加了「无 button 嵌套」断言锁死。

**验证**：`test_v381.py` 56 项（含本地 CRUD 在真实临时目录里跑删除→恢复→彻底删除往返），
10 套回归全绿；`node --check`、HTML 标签平衡与改动前逐项对比、computed/methods 交叉校验。

**同日修订（同版本重发）**：发完版用户追问「那如果我在本地文件里面改名的话，会怎么样」。
一查是真空档 —— 判定每次实时重算，基线只记云端集合不记本地对应关系，本地一改名
「下载完毕」就悄悄退回无标识，看起来像没下载完。我上一轮把「同名+同大小」当既有口径
直接继承，没把本地改名这条路径单独想一遍，属考虑漏了。

修法是把「名字比对」升级成「记住映射」：索引带绝对路径，首次打标时把
`{云端签名: 本地绝对路径}` 写进基线；判定优先按路径+大小，路径失效才回退名字索引；
改名 / 移动 / 删除三条本地链路成功后调 `folder_remap_paths()` 同步（删除则移除映射，
让标识正确掉标）。云端改名改按「净增」算 `added`，一进一出不再误报「有更新」，
并用 `folder_transfer_map()` 按大小把旧路径转给新签名。

设计上有两个刻意的选择：① 旧基线没有 `map` 字段也能平滑升级，首次判定自动补映射，
不做数据迁移、不清用户状态；② 单文件的「已下载」绿标仍走纯名字索引，不改它 —— 那是
v3.81 之前就有的行为，改它会牵动 `dirs` 的热路径，收益不抵风险。代价是改名后
**单文件绿标会掉、文件夹「下载完毕」不掉**，已在 CHANGELOG 里写明。

补了 20 项端到端回归（真实临时目录跑「判定→改名→移动→云端改名→新增→确认→删除」全链路），
10 套回归全绿。NAS 当时还没升级，所以直接重构建覆盖 v3.81 的 Release 资产，没另起版本号。

**修订二（同日 22:50）：分享链接 PROHIBITED 排障**。用户截图报
「分享不可用（PROHIBITED）：链接可能已过期、被删除或提取次数用尽」。我先按常规思路
怀疑分享被封，做了一串对照：换 4 个账号全 PROHIBITED、连跑 5 次稳定、`myshares`
43 条自建分享状态只有 OK/EXPIRED/DELETED、拿 3 条自建正常分享走同一 `shareparse`
全部成功 —— 只能证明「本地一切正常」，说明不了服务端为什么拒。

用户补了一句「电脑主机上有代理可以打开，NAS 控制台打不开」，方向才对：是**出口 IP
地区限制**。再查发现 NAS 上 mihomo 活着（v1.19.33、49 节点、当前 🇭🇰香江-F，
之前全超时的状况已恢复），但控制台 `netMode=direct` + `proxyUrl=''`，
`proxy_url()` 返回空 —— **代理在机器上跑着，控制台根本没用它**。
临时切到 `127.0.0.1:7890` 后状态码从 PROHIBITED 变成 NOT_FOUND（换出口服务端态度就变），
且代理比直连慢 4 倍（2.4s vs 0.6s），全局切代理会拖累下载，不可取。

最终修法：复用 `proxyUrl` 这个「可预置、可不启用」的既有字段 —— 填地址即可，
`shareparse` 遇到 PROHIBITED / NOT_FOUND 时**只让分享解析**改走该地址重试一次，
下载 / 云盘 / 封面仍直连，不用切全局模式，也不用新增设置项或改前端。
顺带把 `_pk_http` 的 `proxy` 改成可接受地址字符串，显式指定时失败**不再静默回落直连**
（这个静默回落以前会让人误以为代理试过了，是排障时最容易踩的坑）；
`pk_share_info` / `pk_share_detail` 走同一条路径，避免换出口后 token 不通用。
错误文案按 share_status 分类并带出 `share_status_text`。

**教训**：`proxycheck` 的「直连可用 358ms」只测到达性（401/404 都算通），
测不出业务层的地区封禁 —— 别拿它当「直连没问题」的证据。另外用户说「有代理」
时，要先确认**控制台有没有真的启用**，机器上跑着 ≠ 程序在用。
