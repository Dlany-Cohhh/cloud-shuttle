# 用提示词让 AI 审「云梭」的完整性 && Bug

> 面向本仓库的实测版提示词手册。基线：`download-console.py` 11,927 行单文件后端 + `static/app.js` 97 处 `api()` 调用 + 22 个 `tests/` 文件 341 用例。
> 实测日期 2026-11-26：`py_compile` 通过，22/22 测试文件全绿（不代表没有 bug，只代表基线干净）。

---

## 0. 先搞清楚：什么事不该交给 AI

| 检查类型 | 谁来做 | 原因 |
|---|---|---|
| 语法 / 导入 / 类型明显错误 | `py_compile`、`python -m unittest` | 秒级、零幻觉 |
| 未定义变量、拼写错误 | 静态工具（pyflakes / ruff） | AI 会漏，工具不会 |
| 接口是否对齐、状态机是否闭环、并发是否有洞 | **AI** | 需要跨文件、跨函数推理 |
| 文档承诺的功能是否存在 | **AI** | 需要读自然语言再对代码 |

所以正确姿势是：**先跑机械检查拿到干净基线，再让 AI 只做「语义审计」**。AI 在 11,927 行的文件里如果没有基线，会大量报告「已通过编译的假问题」。

### 机械基线（先跑，把结果贴给 AI）

```powershell
cd E:\A-MyProject\cloud-shuttle
python -m py_compile "download-console.py";   # 语法
Get-ChildItem tests\test_*.py | ForEach-Object { python $_.FullName }   # 逐文件跑（tests/ 无 __init__.py，unittest discover 会报 not importable）
```

## 1. 一条好提示词的四个必备要素

本项目的 AI 审查提示词，缺一条就会退化成「看起来很专业但不可复核」的散文。

1. **范围**：明确到文件 + 行号区间或符号清单。禁止「帮我看看整个项目」。
2. **判定标准**：什么算 bug、什么算不完整，写成可判定的规则（例：前端 `api("x")` 在后端没有 `action == "x"` 分支 = 缺陷）。
3. **证据要求**：每个结论必须带 `文件:行号` + 原文片段，禁止只写函数名。
4. **输出格式**：分级表格（严重/中/低 + 触发条件 + 影响 + 最小复现），并要求标注置信度、允许写「待验证」。

> 反模式：「请仔细检查代码是否有 bug」。这句话只会换来一份安全但无用的摘要。

## 2. 可直接复制的提示词

### A. 完整性审计：前后端接口对齐（本项目性价比最高的一条）

```
你是这个仓库的代码审计员，只做一件事：前后端接口一致性全量审计。

背景：
- 后端是单文件 download-console.py，HTTP 服务手写在 do_POST（约 11800 行起），
  所有业务接口走同一个 POST /api，用请求体里的 action 字段做 if/elif 分发（约 9261 行起）。
- 前端 static/app.js 通过 api(action, body) 调用（helper 约 1062 行），共 97 处调用。
- 接口文档是 docs/API.md。

任务，四步，一步都不许省：
1. 从 static/app.js 提取全部 api("...") 的 action 字面量，列成集合 F（含行号）。
2. 从 download-console.py 的 action 分发链提取全部分支键，列成集合 B（含行号）。
3. 从 docs/API.md 提取文档中声明的接口，列成集合 D。
4. 输出差异表，只列不匹配项：
   - F 有、B 无 → 前端孤儿调用（点了报「未知 action」）
   - B 有、F 无 → 后端死接口（可能是历史遗留或前端漏接）
   - B 有、D 无 → 未文档化接口
   - D 有、B 无 → 文档承诺但没实现（最严重的完整性缺陷）
   - 同名但大小写/下划线不一致 → 实际是断链，算缺陷

输出格式：Markdown 表格，列 = [类型, action 名, 前端行号, 后端行号, 文档位置, 判定, 证据原文片段]。
要求：全量比对，不许抽样；比对前先自查是否漏提取（例如动态拼接的 action、别名变量）。
如果某个 action 名是变量而非字面量，单独列一节「无法静态判定」，并说明原因。
```

### B. Bug 猎杀：按子系统分块，不要一次吞全文件

一次只审一个子系统，每个子系统给固定三视角：**状态机 / 并发 / 资源**。

```
审查范围：download-console.py 的「任务生命周期」子系统，符号包括
launch_job(2511)、_JobAbort(2609)、unfinished_entries(2617)、build_live_transferring(2627)、
stop_job_group(2672)、sweep_orphan_groups(2695)、wait_worker_exit(2762)、auto_retry_scan(1908)。

只读这些符号及其直接调用者，不要扩散到全文件。

按三个视角逐条排查，每个视角至少给 3 条结论：
1. 状态机：job 的 排队/下载中/暂停/出错/完成 之间是否存在非法跃迁？收尾时是否会把在飞文件算成 done？
   暂停后重试是否会重复计数？删除记录时后台线程是否仍在写同一个 job_id？
2. 并发：多线程同时改 jobs 字典 / settings / name_map 是否有锁或原子写？_write_json 是否可能被并发写坏？
   两代 worker 是否会并存（v4.16–v4.18 修过，检查是否还有残留路径）？
3. 资源：AbortController / 线程 / 临时目录 / 半截文件 在异常路径（异常抛出、进程被杀、rclone rc 超时）是否泄漏？

每条结论必须包含：严重度(高/中/低) | 触发条件（具体到参数或时序） | 影响面 | 最小复现步骤 | 证据 文件:行号 + 原文片段 | 置信度(高/中/低)。
不允许把「代码风格」写进结论；不允许只写函数名不写行号；证据不足的写「待验证」并说明需要什么才能确认。
最后单列一节「我验过的、确认没问题的点」，避免只报坏消息造成误判。
```

同一模板换子系统即可：**通知**（notify_scan 1746 / notify_sig 1624 / _notify_state_save 1650，重点查去重与状态跃迁是否重播）、**命名落盘**（safe_basename 2240 / dedupe_dest 2043 / name_map 2296–2392，重点查超长名截断、同名冲突、跨卷映射）、**网络代理**（rc 372 / refresh_proxy_rc 711 / _rc_http_call 348，重点查重试、超时、凭证失效判定）。

### C. 前端一致性：字段名和事件名最容易错

```
审计 static/app.js 与 static/index.html 的一致性，范围只到这 3 类问题：
1. 后端返回值字段名 vs 前端读取字段名：挑 20 个高频 action（jobs / settings / remotes / verify 等），
   逐字段对照后端 dict 构造处与前端取值处，列出「后端给 a、前端读 b」的断链。
2. Vue 模板引用的 data 字段在 app.js 里是否真的存在（含 computed / methods），列出幽灵字段。
3. 事件绑定调用的方法名是否存在同名定义（onClick="xxx" 但 app.js 无 xxx）。

输出：表格 [问题类型, 前端位置, 后端位置, 现象（用户看到什么）, 修复建议]。
只报能给出两处行号的确定性问题；猜测的放「待验证」。
```

### D. 只审这次改动（日常最该用的一条）

```
只审 git diff 的未提交改动，不审全仓。对每一处 hunk 回答三个问题：
1. 改动的意图是什么（用一句话复述，如果我理解错了请指出）。
2. 是否引入回归：列出所有会走到这段代码的调用点（给行号），逐个判断行为是否变化。
3. 是否有遗漏的对称修改：docs/API.md、README.md、CHANGELOG.md、tests/ 是否该同步却没同步。

输出：按 hunk 分节，每节结论用「安全 / 有风险 / 有 bug」三档，带行号。
如果 diff 超过 300 行，先只审 download-console.py 的部分，其余等我下一轮指令。
```

### E. 补齐回归测试（让 bug 不再回来）

```
给刚确认的 bug 写回归测试，必须完全沿用 tests/ 现有风格：
- 文件顶部用 importlib.util 载入 download-console.py，模块名注册为 dc（照抄 test_autoretry.py 前 20 行）。
- 用 unittest，fake 掉 load_jobs / save_jobs / rc 等外部依赖，不碰真实网络和磁盘。
- 测试名用中文 docstring 说明「在防哪个回归」。

先给出 3 个候选测试点及各自的断言，我确认后再写文件。
写完后自己跑一遍 python tests\test_xxx.py，把输出贴给我。
```

## 3. 对付 11,927 行的分块技巧

不要一次把整文件丢给 AI，它会在前 500 行就形成结论，然后对所有函数套用同一个假设。

- **按行号切**：单次 ≤1,500 行，附一句「你只看到片段，缺失上下文请明说，不要脑补」。
- **给符号清单**：像提示词 B 那样先列出目标函数和行号，比给行号区间更准。
- **两轮制**：第一轮只要「审查计划 + 疑点清单（不含结论）」；第二轮挑 3–5 条深挖。省 token，也避免它一次糊完。
- **强制自证**：追加一句「对每条结论，说明你是从哪一行代码推出来的；如果只是名字像，请降级为待验证」。

## 4. 闭环：AI 报的每一条都要能落地

```
AI 报缺陷 → 你 5 分钟内写个最小复现（脚本 / 加一条断言 / 对照日志）
   ├─ 复现成功 → 修 → 写回归测试（提示词 E）→ 跑全量 341 用例
   └─ 复现失败 → 回给 AI「这条按现有代码不成立，原因 X，请复核或撤回」
```

三个高频翻车点，提前在提示词里堵住：

1. **礼貌性通过**：「整体实现良好，未见明显问题」——这是没审。要求「每个视角至少 3 条结论」可破。
2. **虚构行号**：要求贴原文片段，片段和行号对不上就能识别。
3. **把设计取舍当 bug**：本项目明确「无数据库、JSON 文件存状态、无鉴权」，AI 常把「没有锁/没有鉴权/没有事务」当缺陷。在提示词里加一句「已知设计取舍：单机内网、JSON 持久化、无鉴权，不要作为缺陷上报（除非能证明会导致数据损坏）」。
